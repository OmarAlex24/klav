The output, with the values taken out.

klav agent run puts the values in the command's environment and hands the output to the agent only once the command ends, with every value replaced by [redacted by klav]: as written, or in base64, hex, URL encoding or escaped JSON.

It's a safety net for accidents. A command that encrypts or reshapes a value on purpose can still get it out.

No .env to read.

klav.toml lists references, not values, so it goes in the repo with the code. klav run -- npm run dev resolves them when the process starts. Klav doesn't block a cat .env; there's just no .env left to read.

If a tool insists on a file, klav inject --fifo hands it the value through a pipe that can be read once.

Your personal agent, too.

The agent you built signs in to sites with your passwords and passkeys, and never sees them. It asks Klav to fill the login, with fill_login in klav mcp or with klav agent fill. Klav types the values into the page in your browser, and the agent gets back the names of the fields it filled, never the values. Passkeys work inside a task you approved: Klav signs in, and the agent never gets the key.

It has to run on the computer where your browser is. If it also drives the page with scripts or DevTools, it can read a field after Klav fills it.

Your tokens never enter the sandbox.

Agents reach Northflank, or any HTTPS API you list, through a proxy that adds the real token on the way out. The sandbox only gets a credential that dies with it. Run the proxy yourself today, or, in the invited beta, use Klav Cloud’s, inside an enclave your devices verify.

  • Sealed memoryNo one can log in to the enclave, and it has no disk. Root on the host, Klav's operators and AWS's staff can't read its memory. A debug console would zero its measurements, and your devices would refuse it.
  • Your device checks firstBefore it wraps a token for the enclave, your Mac, iPhone or the CLI checks a fresh attestation signed by AWS's hardware (ECDSA P-384, chained to AWS's Nitro root) and compares PCR0, PCR1 and PCR2 with a signed manifest. One changed byte, and it refuses.
  • Rebuild it yourselfThe code is open and the image builds the same every time. verify-release.sh checks a manifest's signature and rebuilds each listed commit to the same PCRs.manifestsverify-release.shproxy.klav.dev/v1/manifestproxy.klav.dev/v1/manifest
  • Upgrades in the openSandbox traffic ends its TLS 1.3 inside the enclave, at *.proxy.klav.dev, so the host relays only ciphertext. An enclave hands its keys to a new version only once that version's signed manifest is public on GitHub.

What you still trust: AWS's Nitro hardware and its attestation keys, and whoever signs Klav's releases, who would have to publish a bad one where anyone can see it. The host still sees which services you call, when and how much.

Self-hosted proxy
Klav Cloud

With the self-hosted proxy, it's on you to:

  • Keep it running. If it runs on your Mac and the Mac sleeps, sandboxes can't use your tokens until it wakes.
  • Update it when a new version comes out.
  • Protect the machine it runs on. Whoever runs that machine could, in principle, read its memory. To keep even your cloud provider out, run it on a machine with confidential computing.
  • Expose it to your sandboxes through a tunnel or a private network.

What no mode solves:

  • Whoever runs the sandbox sees what the agent sends and receives. The proxy keeps your tokens and your Klav keys out, not the data.
  • While a sandbox lives, the agent can do what the token allows through the proxy. That's what the allow lists and approvals are for.
  • The proxy protects the token, not data the agent decides to send somewhere else.

Browser extension

Needs the Mac app on the same computer or, on Linux, the command line

It isn’t in the browser stores yet, so you install it by hand. It asks Klav’s background service for everything, and holds no keys itself.

Chrome, Brave, Edge, Arc and Dia · preview

  1. Unzip the download into a folder of its own, and keep that folder: the browser runs Klav from it.
  2. Open chrome://extensions, turn on Developer mode, choose “Load unpacked” and pick the folder.
  3. In the Mac app, open “Set up this Mac” › Browsers › “Advanced options” and turn on “Development extension”. With the CLI: klav extension install-host --dev. Then restart the browser.

A preview. Until Klav is in the Chrome Web Store, any unpacked extension that carries the public key from Klav’s source code can talk to Klav’s background service, not only Klav’s. Load only extensions you trust.

Firefox

  1. Open about:addons, click the gear, choose “Install Add-on From File…” and pick the .xpi. Mozilla signed it, so it stays installed.
