This page lists every setting of `klav-server`, with its default, and explains who can register, the quotas per account, the logs and how to send approval notifications to the iPhone. Every setting has a safe default.

## Where settings come from

1. An optional TOML file, with `--config <path>` (or `-c`) or the `KLAV_CONFIG` variable.
2. `KLAV_*` environment variables, which win over the file.

An unknown key in the file is an error, so a typo doesn't pass silently:

```text
klav-server: invalid config file: unknown field `lisen`, expected one of `listen`, `database_url`, `data_dir`, `trust_forwarded_for`, `trusted_ip_header`, `allow_registration`, `registration_mode`, `sessions`, `retention`, `log`, `limits`, `rate_limit`, `push`
```

## Environment variables

| Variable | TOML key | Default | What it does |
|---|---|---|---|
| `KLAV_CONFIG` | — | — | The TOML file's path |
| `KLAV_LISTEN` | `listen` | `127.0.0.1:8080` (`0.0.0.0:8080` in the image) | Address and port |
| `KLAV_DATABASE_URL` | `database_url` | `sqlite://data/klav.db` (`sqlite:///data/klav.db` in the image) | `sqlite://…` or `postgres://…` |
| `KLAV_DATA_DIR` | `data_dir` | `data` (`/data` in the image) | Folder for attachments |
| `KLAV_REGISTRATION_MODE` | `registration_mode` | `open` (`invite` in `docker-compose.yml`, Homebrew and the systemd example) | Who can create an account: `open`, `invite` or `closed`. See [Registration](#registration) |
| `KLAV_ALLOW_REGISTRATION` | `allow_registration` | `true` (`false` in `docker-compose.yml`, Homebrew and the systemd example) | The older switch: `true` means `open`, `false` means `closed`, or `invite` with `KLAV_REGISTRATION_MODE=invite` |
| `KLAV_AUTO_INVITE_TOKEN` | `invites.auto_token` | — | Bearer token of the auto-invite route, at least 32 bytes. See [Auto-issued invites](#auto-issued-invites) |
| `KLAV_AUTO_INVITE_MAX` | `invites.auto_max` | `0` (off) | How many auto-issued invites may exist at once |
| `KLAV_TRUST_FORWARDED_FOR` | `trust_forwarded_for` | `false` | Take the client's IP address from `X-Forwarded-For` |
| `KLAV_TRUSTED_IP_HEADER` | `trusted_ip_header` | none | A header your proxy sets to the client's IP address, such as `x-real-ip`; not with the one above |
| `KLAV_LOG_FORMAT` | `log.format` | `json` | `json` or `pretty` |
| `KLAV_LOG` | `log.filter` | `info` | Log filter, such as `info,klav_server=debug` |
| `KLAV_APNS_KEY_PATH` | `push.apns.key_path` | — | The APNs `.p8` key file |
| `KLAV_APNS_KEY` | `push.apns.key` | — | The `.p8` key's PEM content, instead of the path |
| `KLAV_APNS_KEY_ID` | `push.apns.key_id` | — | That key's ID |
| `KLAV_APNS_TEAM_ID` | `push.apns.team_id` | — | Your Apple team ID |
| `KLAV_APNS_TOPIC` | `push.apns.topic` | — | The iPhone app's bundle ID |
| `KLAV_MAX_ACCOUNT_ATTACHMENT_BYTES` | `limits.max_account_attachment_bytes` | `10737418240` (10 GiB) | Attachments per account. See [Quotas](#quotas-per-account) |
| `KLAV_MAX_ACCOUNT_VAULT_BYTES` | `limits.max_account_vault_bytes` | `1073741824` (1 GiB) | Encrypted vault data per account, besides attachments |
| `KLAV_MAX_ITEMS_PER_ACCOUNT` | `limits.max_items_per_account` | `100000` | Items per account |
| `KLAV_MAX_VAULTS_PER_ACCOUNT` | `limits.max_vaults_per_account` | `1000` | Vaults per account |

Booleans take `true`/`false`, `1`/`0` and `yes`/`no`. For the two IP settings, see [The client's IP address](/self-hosting/tls-and-reverse-proxy/#the-clients-ip-address).

## The whole TOML file

Every key, with its default. `[push.apns]` has no default and stays commented out:

```toml
listen = "127.0.0.1:8080"
database_url = "sqlite://data/klav.db"
data_dir = "data"
trust_forwarded_for = false
# trusted_ip_header = "x-real-ip"   # or this one, never both
allow_registration = true
registration_mode = "open"     # or "invite" or "closed"; see Registration

[sessions]
access_ttl_secs = 900          # access token: 15 min
refresh_ttl_secs = 2592000     # refresh token: 30 days, renewed on each use

[retention]
trash_days = 30                # trash and deleted vaults, before they are purged
purge_interval_secs = 3600     # how often the purge runs

[log]
format = "json"
filter = "info"

[limits]
max_json_body_bytes = 4194304         # 4 MiB per JSON request
max_meta_bytes = 65536                # metadata of a vault or project
max_overview_bytes = 65536            # an item's overview section
max_details_bytes = 1048576           # an item's details section
max_item_versions = 50                # earlier versions kept per item
max_attachment_bytes = 104857600      # 100 MiB per attachment (encrypted)
max_attachment_chunk_bytes = 8388608  # 8 MiB per upload chunk
max_pending_upload_bytes = 1073741824 # 1 GiB of unfinished uploads per account
max_account_attachment_bytes = 10737418240 # 10 GiB of attachments per account; 0: no limit
max_account_vault_bytes = 1073741824  # 1 GiB of vault data per account; 0: no limit
max_items_per_account = 100000        # 0: no limit
max_vaults_per_account = 1000         # 0: no limit

[rate_limit]                   # token buckets: refill per minute, and burst
ip_per_minute = 600            # every request, per IP address
ip_burst = 120
auth_ip_per_minute = 30        # prelogin, registration, login and refresh, per IP address
auth_ip_burst = 10
auth_email_per_minute = 10     # attempts per email and IP address
auth_email_burst = 5
account_per_minute = 1200      # signed-in requests per account
account_burst = 300
invite_ip_per_minute = 1       # invite checks and failed invites, per IP address
invite_ip_burst = 10

# Approval notifications to the iPhone: off by default.
# Uncomment key_path (or key), key_id, team_id and topic; with one missing,
# the server doesn't start.
# [push.apns]
# key_path = "/run/secrets/AuthKey_<KEY_ID>.p8"
# key = """-----BEGIN PRIVATE KEY-----…"""  # or the content, never both
# key_id = "<KEY_ID>"
# team_id = "<TEAM_ID>"
# topic = "<your bundle ID>"
```

Over a limit, the server answers `429` with `Retry-After`. Limits per IP address group IPv6 addresses by their `/64`. The sign-in limit per email counts by email **and** IP address, so someone who knows your email can't lock you out from another network.

## Registration

`registration_mode` decides who can create an account on your server:

- **`open`:** anyone who reaches it. The default of the bare binary, as before invites existed.
- **`invite`:** only someone with an invite code you create with `klav-server invite create` (see [Invites](/self-hosting/quick-start/#invites)). `docker-compose.yml`, the Homebrew configuration and the systemd example start here.
- **`closed`:** nobody.

`allow_registration` is the older switch, and is still read. When both are set, they must agree, or the server doesn't start: `true` goes only with `open`, and `false` with `closed` or `invite`. Keep `allow_registration = false` (or `KLAV_ALLOW_REGISTRATION=false`) next to `invite`: a `klav-server` from before invites ignores `KLAV_REGISTRATION_MODE` and would otherwise start open to everyone, after a rollback for example. Remove it only to choose `open`.

`/v1/health` reports the mode in `registration_mode`. In `invite` and `closed` mode, `registration_open` is `false`, so an app too old to know invites stops before it asks for a password; update it to sign up with an invite.

### Auto-issued invites

For a sign-up page that emails invites by itself, as `klav.dev` does for Klav's own server. Most self-hosted servers leave this off.

With `KLAV_AUTO_INVITE_MAX` above `0`, a `KLAV_AUTO_INVITE_TOKEN` of at least 32 bytes (`openssl rand -base64 48`) and `registration_mode = "invite"`, the server answers `POST /v1/internal/invites/auto` with `Authorization: Bearer <token>` and `{"email": "…"}`:

- `201` with `id`, `code` and `expires_at` (Unix milliseconds): an invite bound to that email, single-use, expiring in 14 days, with the note `auto-beta`.
- `409` with `"error": "already_invited"` if that email already has one that isn't revoked, used or not.
- `409` with `"error": "cap_reached"` once `KLAV_AUTO_INVITE_MAX` of them exist, not counting revoked ones.

`POST /v1/internal/invites/auto/<id>/revoke` revokes an unused one and frees its seat, for when the email with the code couldn't be sent. Otherwise both routes answer `404`, and a missing or wrong token gets `401`. The routes are on the same address as the rest of the API, so the token is what protects them: keep it in your secrets manager. The server never logs the code or the token, and it won't start with a token shorter than 32 bytes, or with a cap and no token.

## Quotas per account

Four limits keep one account from filling the server. `0` turns a limit off. The vault's owner is the one counted.

- **`max_account_attachment_bytes`:** every attachment that isn't purged, finished or still uploading, including those of items in the trash.
- **`max_account_vault_bytes`:** everything else that is encrypted: items with their earlier versions, and the metadata of vaults and projects.
- **`max_items_per_account` and `max_vaults_per_account`:** items in the trash and deleted vaults count until they are purged.

Over a quota, a write that would grow the account gets `403` with a message that names the limit, what is used and the maximum. Edits that don't grow it, deleting anything, moving it to the trash and reading always work, so an account over a quota it was given later can still clean up. A quota on attachments must be at least `max_attachment_bytes`, so that one allowed attachment always fits.

The quotas are per account: nothing caps the sum. On a server with many accounts, keep the disk larger than the accounts times their quotas, or watch it.

## Logs

Logs go to standard output, one JSON object per line:

```text
{"timestamp":"…","level":"INFO","message":"klav-server listening","listen":"127.0.0.1:8080","version":"…","target":"klav_server"}
```

For each request the server logs the method, the route as a template (`/v1/vaults/{vault_id}/items/{item_id}`), the status code and the duration. It never logs bodies, encrypted data, headers (`Authorization` included) or query strings.

When an account is deleted, the log keeps one `account deleted` line with the account's ID in its `account` field, never its email. Keep these lines with your backups: see [Deleted accounts](/self-hosting/data-and-backups/#deleted-accounts-and-backups).

## Approval notifications to the iPhone

Without `[push.apns]`, the server sends no notifications, and the iPhone app sees agents' requests while it is open. To notify the iPhone:

<Steps>

1. In your Apple developer account, create a key with **Apple Push Notifications service (APNs)**. Download its `.p8` file (you can only download it once) and note its Key ID and your Team ID.
2. Give the key to the server, either as a file readable only by the server's user (in Docker, a secret or a read-only volume), in `KLAV_APNS_KEY_PATH`; or as content, the whole PEM with its `BEGIN` and `END` lines, in `KLAV_APNS_KEY`. Line breaks may be written as literal `\n`. Never both.
3. Set `KLAV_APNS_KEY_ID`, `KLAV_APNS_TEAM_ID` and `KLAV_APNS_TOPIC`, the bundle ID of the iPhone app you build and sign (see the last point below).

</Steps>

The four go together. If one is missing, the server doesn't start:

```text
klav-server: invalid configuration: APNs needs KLAV_APNS_KEY_PATH or KLAV_APNS_KEY, KLAV_APNS_KEY_ID, KLAV_APNS_TEAM_ID and KLAV_APNS_TOPIC
```

- The server reads the key when it starts and refuses to start if it isn't a valid P-256 key, without repeating its content. It never logs the key, its signed tokens or the devices' tokens.
- A key given in `KLAV_APNS_KEY` stays in the process's environment, where anyone who can read it sees it. Prefer the file where you can.
- Apple sees that your server notifies a device, when, and the kind of notification with a random ID. Not the agent's name, its reason or the item.
- **Apple delivers a notification only to an app signed by the same team as the key.** The Klav app you get from TestFlight is signed by Klav, so a key of your own reaches only an app you build and sign yourself.
